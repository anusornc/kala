# The production bar is the embedded library

"Production-ready" for Kala v1 means the embedded-library shape: an application pulls `io.github.anusornc/kala` from Clojars and opens a peer in its own process, the way DataScript is used. The networked-service shape — a transactor running as a shared service for other applications over untrusted networks — is deliberately not the v1 bar; the transactor and client remain shipped, tested features (the {peer, client} matrix, the wire protocol, the SIGKILL crash-recovery E2E), but transport security and operational hardening are v2 work.

Considered and rejected: declaring the networked service the bar (auth/TLS, wire hardening, and ops tooling would gate the 48 finished stories behind a second project's worth of work, while the guarantees already proven — parity across engines and access modes, durability before ack — are exactly an embedded database's core promise); declaring open-source product the bar (subsumes both and adds product documentation nobody has asked for yet).

Consequences: story 46's publish (0.1.0 on Clojars, tag-triggered release workflow) completes the bar. The constraints that remain are documented honestly in the README rather than fixed — the file store rebuilds every datom into memory at boot (no compaction in v1, so a store is RAM-bound), there is a single writer on a single node (no replication or HA), and the wire protocol carries no authentication or TLS (deployers bind 127.0.0.1 or trust their network). Two v2 issues carry the deferred hardening: a structured reply for unparseable request frames (today a bad frame kills the connection without an error envelope — found by the project E2E) and transport security for the transactor.
