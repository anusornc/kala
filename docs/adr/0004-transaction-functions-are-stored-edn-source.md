# Transaction functions are stored EDN source, evaluated on the transactor

A transaction function is defined as data — an entity with a `:db/ident` (making it resolvable) and a `:db/fn` bootstrap attribute (position 8, `:db.type/string`) holding the function's EDN source — and invoked by that ident, bare as the op head or via `:db.fn/call`. The source is read and evaluated on the process that runs the transaction (the transactor for clients, the peer for embedded and `with`), in a dedicated fn-env namespace that sees `kala.api` reads and nothing of kala.tx; compilation memoizes through kala.weak-cache keyed by source. This is the only shape the architecture admits: the wire is EDN, so a fn object cannot cross it and client parity would fail; the indexes sort datom values in sorted sets, so the EDN form itself (a seq, not `Comparable`) cannot be a value — source text is forced.

Considered and rejected: peer-only inline fn objects (`[:db.fn/call (fn [db] …)]` — in-process only, breaks the four-combination parity gate); auto-storing inline fns under synthesized idents (transacts entities the user never asked for, visible in `:tx-data`); a `:db.type/fn` value-type enum (cosmetic parity — the stored value is still source text, and a new value type threads value-preds, wire docs, and the enum space for nothing); a data-only conditional DSL (invents a language and diverges from the DataScript semantics this project adopts as its reference corpus); sandboxed evaluation (refer-filtering is unenforceable against Java interop — security theater); user-declared `:db/fn` (diverges from Datomic's pre-installed attribute and makes every user re-declare it).

Consequences: the trust model is documented rather than engineered — transact access is code execution on the transactor, the same posture as Datomic. Storage-time validation is structural only (the source reads and evals to an ifn — eager-validation posture); unresolved symbols inside the fn surface at call time as `:transact/bad-tx-fn`. The log records only the expansion: a fn runs once at transact time and replay never re-runs it, so nondeterminism inside a fn (instants, randomness) is log-safe. A fn receives the db value as of its call position — earlier ops of the same tx applied — and its arguments unresolved; its returned tx-data splices in at that position (DataScript sequential semantics).
