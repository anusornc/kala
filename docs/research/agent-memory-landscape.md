# Agent-Memory Landscape: Primary-Source Survey for kala

**TL;DR:** No surveyed system gives agents what kala gives them — datoms with per-transaction provenance, a queryable as-of belief state, write-time schema enforcement, and Datalog joins. The closest competitor on time (Graphiti) offers per-fact validity windows but no whole-graph as-of and no query language; the closest on structure (Graphiti's Pydantic ontology) enforces types but not a controlled vocabulary of values; provenance-to-source exists (Graphiti episodes, mem0's audit log) but is never first-class, joinable data.

*Surveyed 2026-10-16. Every claim traces to an official paper, doc page, or source file; the URL is inline. Claims resting on source code cite the specific file. The landscape moves fast — Letta and mem0 both changed their core memory models within the last year.*

## 1. Letta (MemGPT)

**Paper.** MemGPT (arxiv [2310.08560](https://arxiv.org/abs/2310.08560)) frames memory as "virtual context management" inspired by OS paging: the LLM itself decides what moves between a fast in-context tier and slow external tiers, using interrupts for control flow ([abstract](https://arxiv.org/abs/2310.08560)). The context document sent to the model has three sections: (1) *system instructions* (read-only), (2) *working context* — "a fixed-size read/write block of unstructured text, writeable only via MemGPT function calls," and (3) a *FIFO message queue* whose first entry holds "a system message containing a recursive summary of messages that have been evicted." External context is *recall storage* (every message logged indefinitely) and *archival storage* — "a read/write database storing arbitrary length text objects," implemented on PostgreSQL+pgvector with HNSW cosine search ([full text](https://ar5iv.labs.arxiv.org/html/2310.08560)). At ~70% of the window a "memory pressure" warning is injected; at the flush threshold (~100%) a batch (e.g., 50%) is evicted and summarized recursively. Evicted messages remain in recall storage; archival retrieval is paginated "to prevent retrieval calls from overflowing the context window."

**Current product (2026):** the docs have been rebuilt around a new agent model. The V1 Python API server is archived on the `archive` branch and "the current source code lives in letta-ai/letta-code" ([repo README](https://github.com/letta-ai/letta)). Memory is now **MemFS**: "a git-backed memory filesystem" that is "part of the agent's state" — every edit is git-committed, root files (`MEMORY.md`, `persona.md`, `human.md`) load into the system prompt every turn, subdirectories stay out of context until the agent reads them with ordinary file tools, and there is no semantic index by default ([MemFS](https://docs.letta.com/concepts/memfs)). The paper-era memory-block model persists as blocks attached to agents: a block is a `{label, description, value, limit, read_only}` record, "pinned to the system prompt," renderable "in an XML-like format," with `chars_current`/`chars_limit` visible to the agent; writes are last-write-wins ([memory blocks](https://docs.letta.com/guides/agents/memory-blocks), [memory](https://docs.letta.com/guides/agents/memory)).

**Self-editing tools.** The archived server's function set is the paper's implementation: `core_memory_append`, `core_memory_replace`, `conversation_search` (with `start_date`/`end_date` params, hybrid text+semantic), `archival_memory_insert`, `archival_memory_search` (semantic, with datetime params), plus `memory_insert`, `memory_replace`, `memory_rethink`, `memory_apply_patch`, `memory_finish_edits`, and a unified `memory` tool ([base.py, archive branch](https://github.com/letta-ai/letta/blob/archive/letta/functions/function_sets/base.py)). Current docs add "dreaming": background subagents that "review recent conversations, consolidate useful lessons, and update memory," triggered after N steps or at compaction, plus `/doctor` to audit "placement, duplication, and system-prompt token usage" ([configuration/memory](https://docs.letta.com/configuration/memory)).

- **Time model:** none as a query primitive. You get git history of memory files, a timestamped message log, and date-range parameters on search tools — not an as-of query over what the system believed.
- **Retention:** block `limit` chars is the only hard cap; summarization (paper FIFO eviction) and dreaming consolidation are the compaction mechanisms; recall/archival grow without explicit eviction policy in the docs.
- **Schema ownership:** developer defines block/file structure (labels, descriptions, limits, frontmatter `name`/`description`); the agent owns content within those constraints ([MemFS](https://docs.letta.com/concepts/memfs), [blocks](https://docs.letta.com/guides/agents/memory-blocks)).
- **Integration:** TypeScript Agent SDK, desktop/CLI apps, Letta Cloud, and a hosted MCP server at `https://api.letta.com/mcp` whose tools (`list_agents`, `create_agent`, `send_agent_message`, `get_reply`, ...) expose *stateful agents*, not a memory query surface ([hosted MCP](https://docs.letta.com/platform/hosted-mcp)).

## 2. Zep / Graphiti

**Paper.** Zep (arxiv [2501.13956](https://arxiv.org/abs/2501.13956)) is a "memory layer service for AI agents" whose core, Graphiti, is a "temporally-aware knowledge graph engine" that "dynamically combines unstructured conversation data with structured business data while preserving historical relationships"; it reports 94.8% vs 93.4% (MemGPT) on DMR and up to +18.5% accuracy with 90% lower latency on LongMemEval ([abstract](https://arxiv.org/abs/2501.13956)).

**Data model (source).** The graph holds four element kinds ([README](https://github.com/getzep/graphiti)): *Episodes* — "raw data as ingested — the ground truth stream. Every derived fact traces back here"; *Entities* — nodes "with summaries that evolve over time"; *Facts* — edges "Entity → Relationship → Entity with temporal validity windows"; and *Custom Types* — "developer-defined entity and edge types via Pydantic models." Node/edge fields in code ([edges.py](https://github.com/getzep/graphiti/blob/main/graphiti_core/edges.py), [nodes.py](https://github.com/getzep/graphiti/blob/main/graphiti_core/nodes.py)): `EpisodicNode{content, source, source_description, valid_at, entity_edges, episode_metadata}`, `EntityNode{name, labels, name_embedding, summary, attributes}`, `CommunityNode{name, summary}`, `EntityEdge{fact, name, fact_embedding, episodes: list[episode ids], valid_at, invalid_at, expired_at, reference_time, created_at}` — with `invalid_at` = "when the fact stopped being true" and `expired_at` = "when the node was invalidated." The four-timestamp semantics are documented on the Zep side ([facts](https://help.getzep.com/v4/facts.md)): `created_at` = "time Zep learned that the user got married," `valid_at` = "time the user got married," `invalid_at` = "time the user got divorced," `expired_at` = "time Zep learned that the user got divorced." The docs add that these bounds "do not establish that the source content or the derived fact is true."

**Invalidation (source).** Contradiction handling is two-stage ([edge_operations.py](https://github.com/getzep/graphiti/blob/main/graphiti_core/utils/maintenance/edge_operations.py)): an LLM is shown duplicate candidates plus an "invalidation candidate set" and returns `contradicted_facts` indices — it only *nominates*; then `_apply_temporal_invalidation` applies deterministic date comparisons (e.g., `edge.invalid_at = resolved_edge.valid_at; edge.expired_at = utc_now()`), no thresholds. "Old facts are invalidated — not deleted," so you can "Query what's true now, or what was true at any point in time" ([README](https://github.com/getzep/graphiti)). Precisely: point-in-time is per-fact validity-window filtering; there is no API that returns the whole graph (entities, communities, summaries) as it was believed at time T, and no rollback.

**Retention.** Invalidated facts accumulate; communities — "groups of related entity nodes" with a summary "that collates the summaries held on each of its member entities" — are built manually via `graphiti.build_communities()` using label propagation, and rebuilding "removes the existing communities before it creates new communities" ([communities](https://help.getzep.com/v4/graphiti/core-concepts/communities.md)).

**Context assembly.** Zep's default Context Block is fetched via `thread.get_context`, auto-searching with "the four most recent messages" as query, returning a text block: a `<USER_SUMMARY>` paragraph plus `<FACTS>` entries formatted `"FACT (Date range: from - to)"`, e.g. `"Emily is experiencing issues with logging in. (2024-11-14 02:13:19+00:00 - present)"` ([retrieving-context](https://help.getzep.com/v4/retrieving-context.md)). Custom templates support `%{user_summary}`, `%{edges limit=10}`; advanced construction lets you format facts with `format_fact(edge)` and instructs consumers to "clearly mark any fact with a non-null `invalid_at` as no longer valid" ([advanced-context-block-construction](https://help.getzep.com/advanced-context-block-construction)). No token budget exists — only result `limit`s; the default "prefers recall over precision."

**Schema ownership.** Optional developer-defined Pydantic entity/edge types ("Prescribed & Learned Ontology"); otherwise auto-extraction. Attributes remain `dict[str, Any]`, typed only when prescribed ([README](https://github.com/getzep/graphiti)).

**Integration.** Python SDK; graph backends Neo4j 5.26, FalkorDB 1.1.2, Amazon Neptune (Kuzu deprecated); Apache-2.0; Graphiti ships an experimental MCP server (tools include `add_memory`, `search_nodes`, `search_memory_facts`, `get_episodes`, `build_communities`, `add_triplet`, `clear_graph`; [MCP docs](https://help.getzep.com/v4/graphiti/getting-started/mcp-server.md)) and Zep Cloud ships a context MCP at `https://api.getzep.com/mcp` with read tools `search_graph`, `get_user_summary`, `get_subgraph`, `get_node_neighbors`, `list_episodes` and optional writes `add_memory`/`add_memory_to_graph` ([context MCP](https://help.getzep.com/v4/context-mcp-server.md)). Zep the managed product runs a proprietary "Context Lake" on its own graph database (Konig) rather than third-party backends ([overview](https://help.getzep.com/graphiti/getting-started/overview.md)).

## 3. mem0

**Paper.** Mem0 (arxiv [2504.19413](https://arxiv.org/abs/2504.19413)) runs a two-phase pipeline: extraction of "a set of salient memories Ω" from a message pair with a conversation summary + last-10-message window, then an update phase where the LLM "determines which of four distinct operations to execute": **ADD** (no semantically equivalent memory exists), **UPDATE** (augment existing), **DELETE** (remove contradicted), **NOOP** (no change) ([full text](https://ar5iv.labs.arxiv.org/html/2504.19413)). The graph variant **Mem0g** stores a directed labeled graph G = (V, E, L) in Neo4j, where nodes carry embeddings and "a creation timestamp t_v," updates are resolved by an "LLM-based update resolver" that marks obsolete relationships invalid "rather than deleting them ... to enable temporal reasoning," and retrieval is dual: entity-centric subgraph exploration plus semantic triplet matching.

**Product (2026) diverges from the paper.** The current OSS `add()` is a "V3 PHASED BATCH PIPELINE" with **one** LLM call and an additive-only prompt: the code parses a `memory` list and emits only `"ADD"` events; UPDATE/DELETE now exist solely as explicit `update()`/`delete()` API calls ([main.py](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py)). Deduplication is exact-string only (`hashlib.md5(text.encode()).hexdigest()`), so semantic duplicates are not consolidated in the OSS path. Graph memory has been **removed from the OSS SDK** — "All external graph store drivers (Neo4j, Memgraph, Kuzu, Apache AGE, Neptune) and their code paths (~4000 lines)" were deleted ([migration doc](https://docs.mem0.ai/open-source/graph_memory/overview)) — and re-emerged as an always-on Platform feature whose "graph" is entity co-occurrence links: Mem0 "does not assign typed, labeled relationships," connections are inferred from co-occurrence, and the graph "affects ranking, not the response shape" ([platform graph memory](https://docs.mem0.ai/platform/features/graph-memory)). This is a substantial retreat from the paper's Mem0g (typed triplets, soft invalidation, Neo4j).

- **Time model:** a read-only audit log. `GET /v1/memories/{memory_id}/history/` returns entries with `event` ∈ {`ADD`,`UPDATE`,`DELETE`}, `old_memory`, `new_memory`, `input` (the triggering messages), `created_at`/`updated_at` ([history API](https://docs.mem0.ai/api-reference/memory/history-memory)); the SQLite `history` DB records the same ([main.py](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py)). No rollback exists — "Retrieve the history of a memory" is read-only, and source shows nothing reconstructs vectors from history. The README claims "Temporal Reasoning" for time-aware retrieval in the new algorithm, but the page documents no as-of query ([README](https://github.com/mem0ai/mem0)).
- **Retention:** the paper pipeline bounded memory by consolidation (DELETE/UPDATE); the current OSS pipeline is explicitly additive — the README's "Single-pass ADD-only extraction -- one LLM call, no UPDATE/DELETE" means "memories accumulate" ([README](https://github.com/mem0ai/mem0)) — so unbounded growth is now a property of the OSS algorithm, moderated only by MD5 dedup.
- **Context assembly:** `search(query, filters)` returns "an array of memory documents" with scores/metadata/timestamps; the developer composes the prompt ([search](https://docs.mem0.ai/core-concepts/memory-operations/search)). No block format, no token budget.
- **Schema:** none enforced; free-text memories, free-form metadata; "Custom Instructions" tailor extraction ([features](https://docs.mem0.ai/open-source/features/overview)).
- **Integration:** Python (`pip install mem0ai`), TypeScript (`mem0ai` npm), CLI, LangGraph/CrewAI/Vercel integrations; library vs Docker self-hosted server vs Cloud platform, with the platform's benchmark numbers including "proprietary optimizations not available in the open-source SDK" ([README](https://github.com/mem0ai/mem0)). Hosted MCP at `https://mcp.mem0.ai/mcp` with 11 tools (`add_memory`, `search_memories`, `update_memory`, `delete_all_memories`, `list_entities`, `list_events`, ...) ([MCP docs](https://docs.mem0.ai/platform/mem0-mcp)); the earlier OSS MCP wrapper repo is archived (Mar 24, 2026) ([mem0-mcp](https://github.com/mem0ai/mem0-mcp)).

## 4. LangGraph / LangChain memory

**Model.** LangGraph splits memory into short-term (thread-scoped state persisted by a *checkpointer*, so "the thread can be resumed at any time") and long-term (a *Store* shared across threads) ([memory docs](https://docs.langchain.com/oss/python/langgraph/memory)). The docs adopt the CoALA taxonomy explicitly, mapping *semantic* = "facts about a user," *episodic* = "past agent actions" (often few-shot examples), *procedural* = "agent system prompt" refined via reflection, citing the CoALA paper ([memory docs](https://docs.langchain.com/oss/python/langgraph/memory)). Semantic memory writes come in two shapes: a **profile** (single continuously-updated JSON doc, "error-prone as the profile gets larger") vs a **collection** (many scoped documents requiring update/delete reconciliation, e.g. via the Trustcall package).

**Store API (source).** Items are addressed by a namespace tuple + key: `Item` has `__slots__ = ("value", "key", "namespace", "created_at", "updated_at")` with `value: dict[str, Any]` whose top-level keys are filterable ([store/base/\_\_init\_\_.py](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint/langgraph/store/base/__init__.py)). `BaseStore` exposes `put(namespace, key, value, index=None, *, ttl=...)`, `get`, `delete`, `search(namespace_prefix, *, query=None, filter=None, limit=10, offset=0, refresh_ttl=None)` (semantic search when the store is constructed with an `IndexConfig` of `dims`/`embed`/`fields`), and `list_namespaces`; deletion is `put` with `value=None`. **TTL is first-class** (`supports_ttl`, `refresh_ttl`) — the only decay primitive in this survey's store APIs.

**LangMem.** The companion library offers hot-path ("Conscious Formation") tools — `create_manage_memory_tool`, `create_search_memory_tool` — and background ("Subconscious Formation") managers that "automatically extract, consolidate, and update agent knowledge"; core functions `create_memory_manager` (with custom Pydantic schemas, instructions, `enable_inserts`) and `create_prompt_optimizer` for procedural memory; persistence is LangGraph's `BaseStore` with hierarchical namespaces like `("acme_corp", "{user_id}", "code_assistant")` resolved via `NamespaceTemplate` ([README](https://github.com/langchain-ai/langmem), [conceptual guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)).

- **Time model:** `created_at`/`updated_at` per item plus TTL expiry; no history log, no as-of, no rollback ([store source](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint/langgraph/store/base/__init__.py)).
- **Retention:** developer-owned throughout — TTL on store items; the docs' technique for long conversations is manual "Filter[ing]" of stale messages; checkpoints accumulate ([memory docs](https://docs.langchain.com/oss/python/langgraph/memory)).
- **Context assembly:** none automatic — `search()` returns `SearchItem`s and the developer formats them; no budget primitives beyond `limit`.
- **Schema:** free-form dicts; optional Pydantic schemas arrive only through LangMem's extraction manager ([langmem guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)).
- **Integration:** Python/JS SDKs, LangGraph Platform (store included in deployments), Postgres/SQLite store implementations under `libs/checkpoint-postgres`/`checkpoint-sqlite` ([repo tree](https://github.com/langchain-ai/langgraph)); no first-party memory MCP server.

## 5. MCP memory precedent

The official reference server lives in `modelcontextprotocol/servers`, which now "house[s] just the small number of reference servers maintained by the MCP steering group" — Memory is one of seven active reference servers ("Knowledge graph-based persistent memory system"), alongside Everything, Fetch, Filesystem, Git, Sequential Thinking, and Time ([README](https://github.com/modelcontextprotocol/servers/blob/main/README.md)). What it actually stores, from source ([index.ts](https://github.com/modelcontextprotocol/servers/blob/main/src/memory/index.ts)): `interface Entity { name: string; entityType: string; observations: string[] }` and `interface Relation { from: string; to: string; relationType: string }`, persisted as JSONL — one JSON object per line tagged `"type": "entity"` or `"type": "relation"` — at `memory.jsonl` by default, overridable via `MEMORY_FILE_PATH`; writes are atomic (temp file + rename) behind an in-process mutation queue and a cross-process lock file. The tool surface is nine tools: `create_entities`, `create_relations`, `add_observations`, `delete_entities`, `delete_observations`, `delete_relations`, `read_graph`, `search_nodes` (case-insensitive substring match on name/type/observations), `open_nodes`; the full graph is also exposed as the resource `memory://knowledge-graph` with `notifications/resources/updated` on mutation ([README](https://github.com/modelcontextprotocol/servers/blob/main/src/memory/README.md)).

What it does **not** have, verified in source: **no time fields anywhere** in the data model; **no provenance** (no source/author/confidence — an entity's entire richness is its string-array observations); **no schema enforcement** beyond the two Zod load-time schemas (`entityType` and `relationType` are free strings, no vocabulary); **no retention mechanism** (delete tools exist, nothing automatic). `create_relations` fails if an endpoint entity doesn't exist — referential integrity of entity *names* is the one invariant. This is the shape of memory people actually wire into harnesses over MCP today: a flat file knowledge graph the client LLM curates via tool calls, one `read_graph` dump at a time.

**Registry context.** The official MCP Registry ([modelcontextprotocol/registry](https://github.com/modelcontextprotocol/registry)) is a "community driven registry service for Model Context Protocol (MCP) servers ... like an app store for MCP servers," with a public API at registry.modelcontextprotocol.io (v0.1 API freeze 2025-10-24); it registers `server.json` metadata only, not semantics.

**Notable third-party MCP memory servers** (all covered above with primary citations): Graphiti's experimental MCP server (13 tools over the temporal graph), Zep Cloud's context MCP (read/write over user graphs, OAuth-brokered), mem0's hosted MCP (11 tools over the platform API), and Letta's hosted MCP (exposes stateful *agents* rather than a memory store). Common thread: every serious memory vendor treats MCP as a distribution channel for a hosted store; the official reference server is deliberately minimal.

## Vocabulary: where the taxonomy comes from

CoALA (arxiv [2309.02427](https://arxiv.org/abs/2309.02427)) is the source of the taxonomy agents use today. Its definitions: **working memory** "maintains active and readily available information as symbolic variables for the current decision cycle"; **episodic memory** "stores experience from earlier decision cycles"; **semantic memory** "stores an agent's knowledge about the world and itself"; **procedural memory** is "implicit knowledge stored in the LLM weights, and explicit knowledge written in the agent's code." The operations map is: retrieval reads long-term into working memory; learning writes long-term; and notably "modifying and deleting (a case of 'unlearning') are understudied in recent language agents" — deletion exists in CoALA only as a proposed future direction ([full text](https://ar5iv.labs.arxiv.org/html/2309.02427)). LangGraph's memory docs import this taxonomy verbatim with a semantic/episodic/procedural table ([memory docs](https://docs.langchain.com/oss/python/langgraph/memory)). A kala glossary should either reuse these four terms or deliberately differentiate against them — they are the shared vocabulary of the field.

## Gaps relative to kala

Verified against the sources above; "verified" means the primary source was read (doc page, paper, or source file), not inferred.

**(a) Logic/Datalog joins over memory facts — gap, fully open.** No surveyed system offers unification/joins as a query primitive. Graphiti offers graph traversal and hybrid retrieval (BM25 + embeddings + BFS with distance reranking, [overview](https://help.getzep.com/graphiti/getting-started/overview.md)) — procedural neighborhood expansion, not declarative joins. The MCP server's `open_nodes` returns relations "touching matched nodes" — one-hop expansion ([index.ts](https://github.com/modelcontextprotocol/servers/blob/main/src/memory/index.ts)). mem0's entity links are retrieval-ranking boosts only ("affects ranking, not the response shape," [platform graph memory](https://docs.mem0.ai/platform/features/graph-memory)). LangGraph's `search` supports field filters, not joins ([store source](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint/langgraph/store/base/__init__.py)). **kala primitive:** Datalog queries with joins over datoms — ask multi-hop questions of memory ("preferences of every user who co-occurs with X in sessions after T") as a single query instead of application-side traversal.

**(b) First-class time travel / belief state as-of T — gap, partially occupied.** Graphiti is the only real entrant: bi-temporal `valid_at`/`invalid_at` vs `created_at`/`expired_at` per fact, with deterministic invalidation ([edges.py](https://github.com/getzep/graphiti/blob/main/graphiti_core/edges.py), [edge_operations.py](https://github.com/getzep/graphiti/blob/main/graphiti_core/utils/maintenance/edge_operations.py)); the docs claim temporal fields support "history and point-in-time retrieval" ([facts](https://help.getzep.com/v4/facts.md)) and the README says you can "Query what's true now, or what was true at any point in time." Precisely what it does **not** do: there is no API returning the graph's *state* at T (entity summaries, communities, and episode-derived aggregates are current-only; community rebuilds are destructive), invalidation timestamps are anchored to ingestion time (`expired_at = utc_now()`), and there is no rollback. Letta has git history of MemFS files — versioned memory, checkable-out in principle — but no queryable as-of semantics ([MemFS](https://docs.letta.com/concepts/memfs)). mem0's history is a read-only audit log with no reconstruction ([main.py](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py), [history API](https://docs.mem0.ai/api-reference/memory/history-memory)). LangGraph has `created_at`/`updated_at` only. MCP has nothing. **kala primitive:** `as-of`/`history` reads over the log — every datom is stamped with its tx, so "what did we believe at T" is a query, not a reconstruction.

**(c) Schema-enforced controlled vocabulary at write time — gap, partially occupied.** Graphiti's "developer-defined entity and edge types via Pydantic models" is the closest: prescribed ontologies constrain node/edge types at extraction, but `attributes` is `dict[str, Any]` and attribute *values* have no closed vocabulary ([edges.py](https://github.com/getzep/graphiti/blob/main/graphiti_core/edges.py), [README](https://github.com/getzep/graphiti)). LangMem permits optional Pydantic schemas for *extraction output*, not a store-enforced invariant ([langmem guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)). Letta constrains block *sizes* and read-only flags, not content vocabulary ([blocks](https://docs.letta.com/guides/agents/memory-blocks)). MCP's `entityType` is a free string. **kala primitive:** the schema registry with idents/enums — writes of unregistered idents or out-of-vocabulary enum values are rejected by the transactor, giving the agent's memory a guaranteed enumerable structure (which is exactly what `pull` and Datalog pattern-matching need).

**(d) Provenance on every fact down to the write that asserted it — gap, partially occupied.** Graphiti attaches provenance to source data: "Episodes (provenance): raw data as ingested — the ground truth stream. Every derived fact traces back here," implemented as `EntityEdge.episodes: list[str]` referencing `EpisodicNode`s ([README](https://github.com/getzep/graphiti), [edges.py](https://github.com/getzep/graphiti/blob/main/graphiti_core/edges.py)). But the pointer goes to the *ingested raw datum* (a parsed conversation/document event), not to a transaction, and episodes themselves are LLM-extracted — there is no commit-level record tying a fact to a write with a timestamp, actor, and atomic batch. mem0's history rows carry the triggering `input` messages ([history API](https://docs.mem0.ai/api-reference/memory/history-memory)) — provenance as an audit sidecar, not on the fact. LangGraph items and MCP entities carry none. **kala primitive:** every datom is (entity, attribute, value, **tx**), and every tx carries `:db/txInstant` (and in kala's token-authed single-writer model, a known actor) — provenance is not metadata on facts; it *is* the fact's coordinates, queryable and joinable like any other datom.

**Adjacent strengths worth acknowledging honestly:** Graphiti's invalidation discipline (invalidate-don't-delete with four distinct timestamps) is a genuinely temporal design that predates nothing kala has to beat on correctness — kala's answer is stronger (full as-of over the log) but Zep's productization of "FACT (Date range: from - to)" strings shows what a memory-time UX can look like. LangGraph's TTL is the only first-class decay primitive in the field. And CoALA's admission that "modifying and deleting ... are understudied" ([full text](https://ar5iv.labs.arxiv.org/html/2309.02427)) is the field's own statement of the hole kala's immutable-log-plus-query design fills: correction without loss.
